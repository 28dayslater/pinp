### Bool type handling. 
The type spelling is `bool`. There are two values: `true`, `false`.
Bool literals and variables can be used in arithmetic expressions by promotion to int/float. Example: `fu = bar*baz + (boolvar1 > boolvar2)`.
Bool parameters and literals can of course be used as function arguments and functions can return bool:
```
fu(a:bool, b:bool): bool is a and b or a xor b

fu(a, true)
```

Precedence and associativity of bool operators is just like in C.

Boolean expressions short-circuit like in C.

Boolean operation chains are allowed, provided that they are monotonic:
```
a <= b < c
d >= e >= f > g > h
a == b == c
```

We try to make math folks like pinp ;)

`a != b != c` is not supported.
a < b < c is equivalent to a < b and b < c.
In real world, such chains are usually limited to three elements (`a < b < c`), but we allow more as there is no reason to restrict this syntax.

## In-scope operators

This realises the "forward-looking operator framework" from 0001, dropping the ternary row (it
moves to 0006). Per the human's "just like in C", precedence and associativity match C. Listed
tightest first:

| bp | operators       | fixity | assoc | operands        | result |
|----|-----------------|--------|-------|-----------------|--------|
| 75 | `not`           | prefix | right | bool            | bool   |
| 45 | `< > <= >= == !=` | infix | non-assoc (chains, see below) | numeric | bool |
| 30 | `and`           | infix  | left  | bool            | bool   |
| 25 | `xor`           | infix  | left  | bool            | bool   |
| 20 | `or`            | infix  | left  | bool            | bool   |

The logical operators map to C's **logical** trio `! && ||` (not the bitwise `& ^ |`):

- **`not` joins the unary-minus prefix level (bp 75, from 0001)**, so it binds tighter than every
  infix operator — `not a == b` is `(not a) == b`, like C's `!`. It is right-associative as a
  prefix op: `not not x` = `not (not x)` is allowed (silly, but not worth forbidding). This
  *deviates* from the 0001 forward note, which placed `not` Python-style below the comparisons;
  "just like in C" overrides it.
- **`and` (30) tighter than `or` (20)** — C's `&&` (prec 11) tighter than `||` (prec 12).

**Comparisons are one non-associative band (bp 45) — we diverge from C here.** C splits relational
(prec 6) above equality (prec 7) so it can left-fold them; pinp does not left-fold comparisons at
all — it treats a run of them as a single chaining construct (see *Chained comparison*) — so that
split would be meaningless. One band is the natural home for that construct; *which* combinations
form a valid chain is governed by the monotonicity rule below, not by precedence. This supersedes
the earlier C-relational-above-equality note.

**`xor` is pinp's extension.** C has no logical xor — it ran out of punctuation, not principle (the
symbols went to bitwise `^`), so it never gave one a precedence. pinp adds the English-named
operator and slots it **between `and` and `or`** (bp 25): tighter than `or`, looser than `and`. The
principled reason is the boolean ring over GF(2) — `and` is multiplication, `xor` is addition — so
`and` binds tighter than `xor` just as `*` binds tighter than `+`, giving sum-of-products
(`a and b xor c and d` = `(a and b) xor (c and d)`) without parens. Unlike `and`/`or`, `xor` cannot
short-circuit — both operands always decide the result.

Comparison (45) binds looser than `+` (60), so the human's `bar*baz + (b1 > b2)` *needs* the parens
— without them it parses as `(bar*baz + b1) > b2`. The example `a and b or a xor b` parses as
`(a and b) or (a xor b)`.

## Chained comparison

`a < b < c` reads mathematically — `a < b and b < c` — *not* C's `(a < b) < c` (which compares a
`bool` to `c`, almost always a bug). A run of comparisons at bp 45 desugars, at parse time, to the
`and` of its adjacent pairs:

```
a <= b < c < d   ⇒   (a <= b) and (b < c) and (c < d)
```

- **Desugar, not a new node.** The parser folds the chain into existing comparison + short-circuit
  `and` nodes; sema and codegen need no new cases. A lone comparison (`b1 > b2`) is unaffected — no
  `and` is introduced.
- **Short-circuit falls out of the `and`:** a failing earlier comparison skips the rest, exactly
  like Python.
- **Shared operands are re-evaluated.** `b` above appears in two desugared comparisons and is thus
  generated twice (only on the path where the first comparison passes). pinp functions are pure, so
  this is observably identical to single evaluation — purely redundant work. Revisit (a chain node
  binding each operand to a temporary) only when expressions gain side effects. See *Resolved* #5.
- **Chains must be monotonic.** A chain's operators must all come from one of three buckets, so the
  relation is transitive and reads "across" the chain — exactly what mathematical notation does and
  no more:
  - ascending `{ < , <= }` — `0 <= i < n`, `a < b <= c`
  - descending `{ > , >= }` — `d >= e >= f > g`
  - equality `{ == }` — `a == b == c`

  The buckets are disjoint: an ascending and a descending operator never share a chain (`a < b > c`
  is a parse error — non-transitive, carries no across-chain meaning, and is a classic mistake),
  and `==` does not mix into an ordering chain (`a <= b == c` — write it out). `!=` is **not
  transitive** (`a != b != c` does not mean all-distinct), so it never chains: it is valid only as a
  lone comparison. The error message names the offending pair, e.g. `Cannot chain \`<\` with \`>\`.`

## Type rules

The promotion lattice gains a bottom rung: **`Bool → Int → Float`**.

- `assignable(from, to)` extends to allow `Bool → Int`, `Bool → Float` (and keeps `Int → Float`).
  So a `bool` is a valid argument/return/right-hand-side wherever an `Int` or `Float` is expected;
  the reverse is still rejected (no implicit narrowing to `bool`, mirroring the existing no
  `Float → Int` rule).
- **Arithmetic** (`+ - * / div mod ^`): a `Bool` operand is treated as `Int` (`false`=0,
  `true`=1). Result follows the existing rule on the promoted operands — `/` is always `Float`;
  `div`/`mod` require operands assignable to `Int` (so `Bool`/`Int` ok, `Float` rejected);
  `+ - * ^` are `Int` unless an operand is `Float`. `bool + bool → int`.
- **Comparisons** (`== != < > <= >=`): both operands must be numeric (`Bool`/`Int`/`Float`),
  promoted to their common type, result `Bool`. Mixed kinds promote (`true > 1` is legal: `Bool`
  promotes to `Int`). `Void` operands are an error, as for arithmetic. (Chains desugar to `and`ed
  pairs — see *Chained comparison* — so each pair type-checks under this rule.)
- **Logicals** (`and or xor not`): operands must be exactly `Bool`; result `Bool`. An `Int`/`Float`
  operand is a type error (no truthiness — there is no implicit `Int → Bool`). Feed a comparison
  in instead: `(x > 0) and (y > 0)`.

## Codegen

`Bool` lowers to LLVM `i1`.

- `Node::Bool(b)` → `bool_type().const_int(b as u64, false)`.
- `promote` ([codegen.rs:499](src/codegen.rs#L499)) gains `Bool → Int` (zext `i1`→`i64`) and
  `Bool → Float` (`i1`→`f64` via unsigned-int-to-float); `zero` gains the `Bool` case.
- Comparisons: promote both sides to the common type, then `icmp` (signed predicate) for `Int`,
  `fcmp` (ordered predicate) for `Float`; result `i1`.
- **`and`/`or` short-circuit** — the first intra-expression branching in the codebase, prefiguring
  0006. Each evaluates the left operand, then branches: `a and b` skips `b` when `a` is false; `a
  or b` skips `b` when `a` is true. Lowered as two basic blocks (rhs + merge) joined by a `phi`
  over `i1` — the constant short-circuit value from the entry edge, the rhs value from the rhs
  edge. `gen_expr` must therefore track and append to the current function's blocks.
- **`xor` is eager** (both operands always needed) → `build_xor` on `i1`; `not` → `build_not`.
- **Chained comparison adds nothing here** — it is a parse-time desugar to comparison + `and`
  nodes, which the cases above already lower.

## Resolved (sign-off)

1. **`bool` is unreserved; `true`/`false`/`and`/`or`/`xor`/`not` are reserved.** Type names are
   contextual identifiers (matching `int`/`float`/`void`); value literals and operators are
   keywords.
2. **No implicit `Int`/`Float → Bool`.** Logicals demand `Bool` operands; there is no truthiness.
   This mirrors the existing one-way promotion lattice — `Bool → Int → Float`, never back.
3. **`and`/`or` short-circuit (in scope); precedence follows C's logical `! && ||`.** Short-circuit
   is basic enough to belong with the operators rather than waiting for 0006, so this iteration
   grows the codebase's first basic blocks + `phi` (intra-expression only; statement branching is
   still 0006). `not` takes C's unary-tight position (bp 75), overriding the Python-style placement
   in the 0001 forward note.
4. **`xor` is a pinp extension**, placed between `and` and `or` (bp 25) — `and` tighter than `xor`
   tighter than `or`, the GF(2) ring ordering (`and` = ×, `xor` = +). C has no logical xor, so
   there is no C precedent to match; it is necessarily eager (no short-circuit).
5. **Comparisons chain mathematically, diverging from C.** `a < b < c` ⇒ `a < b and b < c`; the six
   comparison operators form one non-associative band (bp 45), superseding the C
   relational-above-equality split. A chain must be **monotonic** — operators all from one bucket:
   ascending `{ < , <= }`, descending `{ > , >= }`, or equality `{ == }` — so the relation is
   transitive and reads across the chain. Non-monotonic chains are parse errors: mixed direction
   (`a < b > c`), `==` mixed into ordering (`a <= b == c`), and any `!=` chain (`!=` is
   non-transitive, so it is lone-only). Stricter than Python by design — it matches what
   mathematical notation actually permits. Implemented as a parse-time desugar to comparison +
   short-circuit `and` (no new AST/sema/codegen). Shared middle operands are re-evaluated; this is
   observably identical while pinp functions are pure, and is revisited (chain node + temporaries)
   only when expressions gain side effects.
